PRIORITIZED FINDINGS
--------------------
P1. Normalizer and structural-rule vocabulary disagree.
normalizer.py removes repeated Roman vowels; structural_rules.py then tests
literal sets still containing kaapi, keeli and oota instead of kapi/keli/ota.
Exact CSV lookup hides this for known training examples; unseen variants fail.
Confirmed supplied held-out rows:
- q1_2_a: Kaapi beku -> expected accepted/a_tea, actual not_accepted/unclear.
  R00089-R00092 (four format/spelling variants).
- q2_3_b: Dayavittu keeli ellide? -> expected accepted/a_keeli, actual unclear.
  R00500-R00503 (four variants).
- q3_1_a: Nanage oota beku -> expected accepted/a_meal, actual unclear.
  R00555-R00558 (four variants).
- q3_3_a: Oota eshtu? -> expected accepted/a_price, actual unclear.
  R00702,R00703,R00705 (three variants).
Other held-out failures keep rejection outcome but lose wrong_word diagnosis,
e.g. Keeli beku and Keeli elli? in inappropriate steps.
Source: src/normalizer.py; structural_rules.py:5-8, q1_2_a/q2_3_b/q3_1_a/q3_3_a.

P1. Authored {player_name} policy is not implemented for arbitrary names.
feedback.json says any name is accepted; structural rules use Arun/Aditi/Ravi.
The evaluate(player=...) argument is passed through but not used for validation.
Confirmed q1_3_a Nanna hesaru Meera -> not_accepted/incomplete_answer, confidence
0.95; expected accepted/a_name. Hesaru Meera is rejected instead of receiving
missing_possessive correction. q2_1_a name-based correction templates also reject
Meera. Known Arun and Aditi examples pass.
Source: feedback.json answer_rules.placeholders; quests/q1_3.json;
structural_rules.py:88 and q2_1_a; matcher.py:62.

P1. Authored {item} generalization is much broader than actual matching.
feedback.json item_words contains 16 foods/drinks. q1_2_a permits {item} beku and
Nanage {item} beku; q3_1_a permits {item} kodi and Haudu, {item} kodi. Most such
combinations are rejected: Nanage haalu beku, chaha kodi at the meal step,
chapati kodi, dose kodi, and many others. Item expansion accounts for 25 rejected
also_accepted cases at q1_2_a and 26 at q3_1_a in this sweep. Some combinations
only pass accidentally through character similarity (Nanage chapati beku scores
0.889), rather than a reliable item/template parser.
Source: feedback.json item_words; quests/q1_2.json, q3_1.json; authored-mismatches.csv.

P1/P2. Script error can be promoted to accepted by character similarity.
The Kannada anticipated error in q1_2_a (copying the NPC's pronoun: the JSON
e_nimage.kannada field) is explicitly labelled not_accepted/pronoun_mixup but
returns accepted/a_tea with confidence 0.889. The Roman error is correctly rejected.
This is an exact authored-policy mismatch, independent of linguistic judgment.
Source: authored-evaluation.json q1_2_a/anticipated_error/kannada;
matcher.py fuzzy fallback; structural diagnostics mostly operate on Roman words.
Current declared answer mode is Kanglish, so decide script-input scope explicitly.

P2. Global language/error rules are not actually global.
feedback.json says English-only and Hindi input rules apply to every step. Against
all 14 respond steps, Hello is classified english_only only once (13 unclear),
Thank you three times (11 unclear), Chai chahiye hindi_word four times (10 unclear).
All are rejected, so this chiefly loses appropriate pedagogy/NPC reactions.
LanguageDetector.detect is metadata, not a global dispatch/gating step.
One training label itself disagrees: R00855 ALL/ALL what expects unclear but gets
english_only. This is a data/policy decision to review, not an acceptance failure.

P2. Context and negation need semantic review and regression cases.
Targeted q2_2_a Ananya hatra keeli illa is accepted/a_ananya with confidence 0.95;
rules match person+key/location tokens before considering negation. Likewise
Somanna hatra keeli ide Ananya alla is accepted. Review intended meaning and
handling with a fluent Kannada speaker before calling these linguistically final.
The token-set approach also drops order information: Ellide granthalaya returns
accepted, although authored library-first material specifies word_order correction
for the analogous Ellide library case. These targeted probes are separate from
the supplied 178-row measurement.

P2. Automated tests are too weak to guard the learner contract.
Matcher tests assert dict/outcome presence, not that correct answers are accepted.
Structural tests cover only unknown input. None loads responses_test.csv or tests
the content templates. This explains 26 passing tests alongside the failures above.
Script and mixed-language coverage is especially weak: no script held-out rows;
only one mixed held-out row. Detector labels also have inconsistent definitions:
CSV mixed includes English+Kanglish, while detector mixed requires script+Latin.
Ten held-out detected_form labels differ, but this is not used as an accuracy
metric because those label definitions first need harmonizing.

P2. Mastery credit cannot be derived from target_words alone.
q1_2_b has mutually exclusive yes/no answers but target_words includes both haudu
and illa, beku and beda. q3_2 accepts Beda with correction while target_words is
w_saaku; crediting all targets would award a word not produced. q2_2 is name-based
comprehension but its targets include illa and keeli, not produced by saying Ananya.
19/23 say words have target metadata in only one quest. Of four with two-quest
targets, two rely on that comprehension task. Broadened templates create additional
actual production opportunities that the old curriculum summary does not count.
Need response-specific production credit, separate comprehension, and explicit
policy for corrections/help/replays. No mastery event tracker exists in the NLP
component or current TeaProgress save fields.

P2/P3. Hints and success transition behavior need a precise content contract.
feedback.json says a rejected answer gets NPC reaction then quick_hint, whereas
progression.json automatically shows it after two wrong answers. Define first vs
second failure behavior. Mastery says without opening notebook, which alone does
not explain eligibility after viewing full_example or other help. Eleven of 14
respond steps omit npc_reply while README generically says to show it on success;
the data needs an agreed fallback/skip convention, not necessarily eleven new lines.

P3. Spelling CSV has 13 incomplete metadata rows.
Final 13 rows have canonical/variant only; word_id, Kannada, role, rule and verified
are blank. The runtime only requires canonical and variant, so they load, but cannot
be traced/checked like earlier rows. No nonblank unknown word IDs found.
Only two vocabulary entries have variants arrays; broader spelling support lives
separately in CSV. Both formats need a documented source-of-truth/sync procedure.

INTEGRATION AND STORY GAPS (not regressions introduced by this audit)
------------------------------------------------------------------
- No Unity JSON import or references to lesson IDs/AnswerMatcher found in game
  scripts. Unity still advances hardcoded providers through TeaStallSession.Choose.
- Existing HTTP v1 returns text only. Python returns assessment fields and expects
  quest/step identities. The strict current response schema rejects extra fields;
  a structured assessment contract and stable Unity mapping are still required.
- NLP has no HTTP route/server, automatic lesson JSON loader, learner persistence,
  notebook/help tracking, or runtime transliterator. translit_pairs.csv is unused.
- Curriculum assumes conductor thanks, self-naming, wake/polite-gate and a 50-rupee
  lunch task. Current Unity dialogue has its own arrival, tea/library/mess flow and
  longer investigation story; these are not interchangeable quest nodes.
- Existing game notebook/saves are keyed to story flags, not learner mastery.

What remains unverified
-----------------------
Native-speaker grammar, register, transliteration and script shaping/font rendering;
pedagogical difficulty and engagement with real learners; end-to-end Unity/server
behavior; performance at realistic concurrency; all possible unseen spellings and
adversarial inputs. No claim of exhaustive defect discovery is made.

Recommended correction order (not performed): align canonical normalization and
rules; enforce item/name templates; run held-out and policy sweeps in regression;
repair script/negation/global-diagnostic behavior; define mastery/help events;
then map a single reviewed lesson into Unity with a structured assessment contract.
